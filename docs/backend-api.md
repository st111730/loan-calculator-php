# Спецификация бэкенда — калькулятор кредитных заявок

> Документ подготовлен для миграции бэкенда с Node.js (Express) на PHP.
> Здесь зафиксировано текущее поведение API: маршруты, форматы запросов и ответов,
> правила валидации и логика расчёта кредита. Примеров кода нет — только описание контракта.

**Дата актуальности:** 23.10.2026. Изучено по файлам: `server/src/index.js`, `server/src/routes/applications.js`, `server/src/routes/admin.js`, `server/src/lib/loan.js`, `server/src/lib/validate.js`, `server/src/db.js`, `server/src/migrate.sql`, а также по фронтенд-зеркалам (`src/shared/config/loanProducts.ts`, `src/entities/loan/model/credit.ts`, `src/entities/applicant/model/schema.ts`, `src/features/loan-application/model/useLoanCalculatorPush.ts`).

## 1. Общая картина

- **Стек:** Node.js + Express 4 (plain ESM JavaScript, без TypeScript), PostgreSQL через `pg`, валидация `zod`, конфиг из `.env` (`dotenv`). Точка входа — `server/src/index.js`.
- **Порт по умолчанию:** `:4000` (переменная `PORT`). Дев-фронтенд на `:5173` проксирует `/api`; в проде nginx отдает статику и проксирует `/api` и `/admin` на API.
- **Порядок инициализации при старте:** читается `.env` → подключается парсер JSON-тела → регистрируются маршруты → **выполняется миграция БД** (`migrate.sql`, идемпотентная) → сервер начинает слушать порт. Если БД недоступна на старте — процесс падает; если БД недоступна во время запроса — клиент получает HTTP 500 (см. §4.5).
- **Публичный JSON-API — всего два эндпоинта:** `GET /api/health` и `POST /api/applications`. Каких-либо других маршрутов в `/api` нет: список заявок существует только в админке (§4.3).
- **CORS не настраивается** — всё работает по same-origin через прокси. PHP-версии это разрешение не нужно, если сохраняется модель деплоя.

## 3. База данных

Единственная таблица `applications` (создаётся при старте из `server/src/migrate.sql`, только `CREATE TABLE IF NOT EXISTS`):

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | `SERIAL` PRIMARY KEY | Идентификатор заявки |
| `loan_type` | `TEXT NOT NULL` | Идентификатор продукта: `mortgage` / `auto` / `consumer` / `payday` |
| `amount` | `NUMERIC(14,2) NOT NULL` | Сумма кредита, ₽ |
| `term_months` | `INTEGER NOT NULL` | Срок, месяцев |
| `monthly_income` | `NUMERIC(14,2) NOT NULL` | Заявленный месячный доход |
| `full_name` | `TEXT NOT NULL` | ФИО (уже обрезанное по краям) |
| `monthly_payment` | `NUMERIC(14,2) NOT NULL` | Аннуитетный платёж — **пересчитан сервером** |
| `total_repaid` | `NUMERIC(14,2) NOT NULL` | Общая сумма выплат — пересчитана сервером |
| `total_interest` | `NUMERIC(14,2) NOT NULL` | Переплата (проценты) — пересчитана сервером |
| `status` | `TEXT NOT NULL DEFAULT 'new'` | Статус заявки |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | Время создания |

Индексы: `applications_status_idx` (`status`), `applications_created_at_idx` (`created_at DESC`).

⚠️ Механизма миграций с версионированием нет: `migrate.sql` выполняется целиком при каждом старте и содержит только `CREATE ... IF NOT EXISTS`. Схема поднимается для новой БД, но **`ALTER` в этот файл не дойдут до уже существующих баз**. PHP-версии нужно решить: либо повторить идемпотентный автозапуск, либо внедрить настоящий миграционный раннер.

Статусы заявок (константы админки): `new` («Новая», начальный), `in_review` («На рассмотрении»), `approved` («Одобрена»), `rejected` («Отклонена»).

## 4. Эндпоинты

| Маршрут | Метод | Формат | Доступ |
|---|---|---|---|
| `/api/health` | GET | JSON | публичный |
| `/api/applications` | POST | JSON | публичный |
| `/admin`, `/admin?status=…` | GET | **HTML**, не JSON | HTTP Basic |
| `/admin/:id/status` | POST | JSON-тело | HTTP Basic |

### 4.1. `GET /api/health`

- Проверка живости. БД не трогает. Авторизации нет.
- **Ответ 200:** `{"ok": true}`. Другого тела нет.

### 4.2. `POST /api/applications` — приём заявки

Основной (и единственный содержательный) публичный эндпоинт.

**Запрос:** JSON с заголовком `Content-Type: application/json`. Лимит тела — стандартный для Express (~100 КБ). Имена полей — camelCase:

| Поле | Тип | Правила |
|---|---|---|
| `loanType` | string | строго один из: `mortgage`, `auto`, `consumer`, `payday` |
| `amount` | number | **целое**, конечное (не `NaN`/`Infinity`). Отрицательные и ноль отсекаются не отдельной проверкой, а продуктовым диапазоном (§5) |
| `termMonths` | number | **целое положительное**, конечное |
| `fullName` | string | обрезается по краям (trim), затем 2–120 символов; допустимы только буквы кириллицы (вкл. Ё/ё) и латиницы, пробел/любой whitespace, апостроф `'`, дефис `-`. Цифры и прочие символы запрещены |
| `monthlyIncome` | number | положительное, **может быть дробным** (целочисленность не требуется) |
| `hasCitizenship` | boolean | строго `true` (не `1`, не строка `"true"`) |
| `consentGiven` | boolean | строго `true` |

Все перечисленные поля обязательны. **Неизвестные поля молча отбрасываются** (валидатор не в strict-режиме) — PHP-версия может делать то же самое или отклонять; на текущий контракт это не влияет.

**Порядок валидации** (важен для отображения ошибок, см. §5): сначала базовые проверки полей в порядке их перечисления в таблице; если базовые проверки хотя бы одного поля не прошли — продуктовые проверки диапазонов **вообще не выполняются** (в `issues` будут только базовые ошибки). Если всё базовое прошло — проверяются диапазоны: сначала `amount`, затем `termMonths`.

**Сервер не доверяет клиенту:** значения `monthly_payment`, `total_repaid`, `total_interest` из запроса игнорируются полностью — сервер пересчитывает их сам (§6). Клиент их и не присылает.

**Ответ 201 Created:** полная строка таблицы `applications`, ключи — snake_case. Пример (для заявки «Ипотека, 300 000 ₽, 12 мес»):

```json
{
  "id": 42,
  "loan_type": "mortgage",
  "amount": "300000.00",
  "term_months": 12,
  "monthly_income": "50000.00",
  "full_name": "Иванов Иван Иванович",
  "monthly_payment": "27504.00",
  "total_repaid": "330048.00",
  "total_interest": "30048.00",
  "status": "new",
  "created_at": "2026-10-23T12:34:56.789Z"
}
```

Важная деталь сериализации (сейчас): `id` и `term_months` — **числа**, `amount`, `monthly_income`, `monthly_payment`, `total_repaid`, `total_interest` — **строки с двумя знаками** (числовые NUMERIC-колонки драйвер `node-postgres` возвращает строками), `created_at` — ISO-строка. Фронтенд при успехе тело ответа вообще не читает — значение имеет только сам HTTP-статус 2xx (см. §7), поэтому PHP-версия сохранит совместимость, вернув 201 и любой корректный JSON строки заявки; формат выравнивать стоит ради внешних консистентных потребителей, а не ради текущего UI.

**Ошибки 400** (`validation_error`) — по любой проваленной проверке:

```json
{
  "error": "validation_error",
  "issues": [
    { "path": "amount", "message": "Сумма для «Потребительский»: от 50000 до 5000000 ₽" }
  ]
}
```

`issues` — массив всех проблем; `path` — имя поля, склеенное точками (у полей верхнего уровня просто `amount`, `termMonths`, `hasCitizenship` и т.д.; у структурных ошибок тела путь может быть пустым). Фронтенд показывает пользователю **только `issues[0].message`** — первую ошибку. Тексты сообщений — на русском (§5).

**Прочие ошибки:** любое необработанное исключение в обработчике (например, недоступная БД) → 500 `{"error": "internal_error"}` (см. §4.5). Некорректное (битое) JSON-тело сейчас тоже уходит в 500 — парсер JSON бросает ошибку, которую глобальный обработчик не различает.

### 4.3. `GET /admin` — админка (HTML, не JSON)

Сервер-рендеренная страница «Заявки на кредиты». Требует HTTP Basic (`realm="admin"`, логин/пароль из §2); сравнение пароля — защищённое от атак по времени. Без/с неверными кредами → **401** с заголовком `WWW-Authenticate: Basic realm="admin"` и текстом «Требуется авторизация».

- `GET /admin` — все заявки. `GET /admin?status=<один из 4 статусов>` — фильтр по статусу. **Неизвестное значение `status` не даёт ошибки** — просто показываются все заявки.
- Сортировка — по `created_at` (новые сверху). Колонки таблицы: Создана, Продукт, ФИО, Сумма, Срок (мес), Платёж, Доход, Статус; деньги — целые рубли с разделителями и «₽», дата/время — в локали ru-RU. В каждой строке — HTML-форма смены статуса (§4.4).

### 4.4. `POST /admin/:id/status` — смена статуса заявки

- Тоже за Basic-аутентификацией (тот же middleware).
- Тело: `status` — строго одно из `new`, `in_review`, `approved`, `rejected`. `id` — целое число.
- Успех: обновление строки в БД и **302-редирект обратно на `/admin`** (поведение HTML-формы, не JSON API).
- Ошибка (не целое `id` или невалидный `status`): **400**, текст «Некорректные данные» (не JSON).

⚠️ Обнаруженное расхождение текущего кода: глобально подключён только парсер JSON-тел, а форма на странице админки отправляет данные как `application/x-www-form-urlencoded` — такое тело не парсится, и, по всей видимости, **штатная форма всегда падает в 400**. API-контракт при этом подразумевает JSON-тело вида `{"status": "..."}`. При миграции на PHP нужно принять решение: либо парсер форм + urlencoded-тело, либо JSON-эндпоинт — но зафиксировать одно поведение.

### 4.5. Сквозной обработчик ошибок

Один глобальный обработчик на всё приложение: любое исключение → лог в консоль и **500 с телом `{"error": "internal_error"}`**. Статус ошибки не различается (в т.ч. ошибки парсера тела), специальный формат для 404 отсутствует (Express отдаёт штатную HTML-страницу not found — на консистентность JSON API это не влияет, но для PHP стоит решить, как обрабатывать несуществующие пути).

## 5. Валидация заявки — полный свод правил

Логика продублирована контролёром на сервере (`server/src/lib/validate.js`) и на фронтенде (`src/entities/applicant/model/schema.ts`). Содержательно серверные правила совпадают с фронтовыми, кроме текстов: **серверные тексты базовых ошибок типа «не число» — стандартные англоязычные у zod**, а русских сообщений о нарушении диапазонов, наоборот, обоими сторонами одинаковы (см. ниже). Проверки сервера — обязательные; фронтовая валидация лишь повторяет их для мгновенного UX.

Правила (все обязательны, ошибка первой проблемы возвращается в `issues[0].message`):

1. **loanType** — только 4 допустимых перечисленных значения.
2. **amount** — число, целое, конечное; далее продуктовый диапазон: `minAmount ≤ amount ≤ maxAmount`. Сообщение: `Сумма для «{Название продукта}»: от {minAmount} до {maxAmount} ₽` (например: `Сумма для «Ипотека»: от 300000 до 30000000 ₽`).
3. **termMonths** — число, целое, конечное, строго больше 0; далее продуктовый диапазон `minTermMonths ≤ termMonths ≤ maxTermMonths`. Сообщение: `Срок для «{Название продукта}»: от {minTermMonths} до {maxTermMonths} мес`.
4. **fullName** — после обрезки краев длина 2…120; разрешены кириллица (вкл. Ё/ё), латиница, пробельные символы, апостроф, дефис. Серверные тексты базовых ошибок — умолчания валидатора (англ.), не кастомные.
5. **monthlyIncome** — число, конечное, строго > 0; целым быть не обязан; никакой верхней границы и проверок доли платёжа к доходу (см. §7, п. 2).
6. **hasCitizenship** = `true` точно (boolean).
7. **consentGiven** = `true` точно (boolean).

Порядок проверки при фейлах (воспроизводимость `issues`): базовые — по порядку полей схемы (`loanType` → `amount` → `termMonths` → `fullName` → `monthlyIncome` → `hasCitizenship` → `consentGiven`); если какая-то базовая не прошла, продуктовые приостановлены; иначе — сначала диапазон `amount`, затем диапазон `termMonths`.

Если PHP-миграция сохранит эти тексты и этот порядок «первой ошибки», UI продолжит работать без правок.

## 6. Логика расчёта кредита

Рассчёт выполняется **на стороне сервера** (`server/src/lib/loan.js`) на основании `loanType + amount + termMonths` из заявки. Комментарий в коде: «копия конфигурации продуктов и аннуитетной формулы с фронтенда; сервер считает независимо — клиентским числам не доверяем» — дублирование intentional (см. §7, п. 1).

### 6.1. Продукты (ставки и лимиты)

| id | Название | Годовая ставка | Сумма min–max, ₽ | Срок min–max, мес |
|---|---|---|---|---|
| `mortgage` | Ипотека | 18 % (0.18) | 300 000 – 30 000 000 | 12 – 360 |
| `auto` | Автокредит | 23,5 % (0.235) | 100 000 – 5 000 000 | 12 – 84 |
| `consumer` | Потребительский | 22,2 % (0.222) | 50 000 – 5 000 000 | 6 – 84 |
| `payday` | Деньги до зарплаты | 50 % (0.5) | 5 000 – 100 000 | 1 – 12 |

Ставка в коде — доля единицы за год (0.18 = 18 %).

### 6.2. Формула (аннуитет)

1. Месячная процентная ставка: `i = annualRate / 12` (простое деление на 12, без сложного процента).
2. Аннуитетный платёж: **P = S · i · (1 + i)ⁿ / ((1 + i)ⁿ − 1)**, где `S` — сумма, `n` — срок в месяцах.
3. Результаты сохраняются в заявке:
   - `monthlyPayment` = P, округлённое до **2 знаков** (по правилам JS, округление половинок «вверх» для положительных);
   - `totalRepaid` = round2(monthlyPayment × n) — **считается от уже округлённого платежа**, а не от точного;
   - `totalInterest` = round2(totalRepaid − S).

Порядок округлений важен: из-за него `totalRepaid` может отличаться от «идеального» расчёта точного платежа (расхождение до ~`n × 0,005` руб.). PHP-версия должна повторить тот же порядок, иначе суммы в БД не совпадут бит-в-бит с существующими историческими записями и тестами.

### 6.3. Эталонные примеры (готовые кейсы для тестов PHP-версии)

| Продукт | S, ₽ | n, мес | monthlyPayment | totalRepaid | totalInterest |
|---|---:|---:|---:|---:|---:|
| mortgage (18 %) | 300 000 | 12 | 27 504,00 | 330 048,00 | 30 048,00 |
| auto (23,5 %) | 1 000 000 | 36 | 38 970,81 | 1 402 949,16 | 402 949,16 |
| consumer (22,2 %) | 500 000 | 24 | 25 988,49 | 623 723,76 | 123 723,76 |
| payday (50 %) | 50 000 | 6 | 9 589,91 | 57 539,46 | 7 539,46 |

Осторожно с граничными случаями округления: `Math.round` в JavaScript — «half up» без предварительного уточнения младших битов, а `round()` в PHP использует пре-раундинг и может дать другой цент на значениях вида `x.xx5`. Рекомендация для PHP: реализовывать округление «вверх половинки» для положительных чисел так, чтобы совпало с JS, и прогнать граничные значения тестами. Аналогично: если вычисляется через `pow()` — убедиться, что результат `(1+i)ⁿ` в double совпадает с JS (обычно совпадает на IEEE 754, но на экзотических платформах возможен ULP-расход, влияющий ровно на один цент).

## 7. Контракт с фронтендом и замечания для PHP-переписывания

Фронтенд вызывает только `POST /api/applications` (vite-dev-прокси или nginx в проде) и интерпретирует ответ так:

- **`res.ok` (статус 2xx)** → заявка «принята»; тело ответа **не читается вообще**. То есть формат тела успеха не контракт — контракт только статус.
- **Статус не 2xx** → фронт пытается распарсить JSON и показать пользователю `issues[0].message`; если сообщения нет или тело не JSON — универсальный текст вида «Сервер вернул ошибку (статус)».
- **Сетевая ошибка/тип `TypeError`** (сервер лежит, прокси отдал 05, и т.п.) — текст «Не удалось связаться с сервером. Проверьте соединение.»

Итого — минимально обязательный контракт PHP-версии: `POST /api/applications` с тем же URL, JSON-запрос/JSON-ответ, статусы 201/400, поля `issues[0].message` с теми же русскими текстами, `GET /api/health`. Остальное — детали.

**Наиболее важные замечания и потенциальные подводные камни (найдено при анализе):**

1. **Дублирование бизнес-логики.** Ставки/лимиты/формула и валидация существуют двумя копиями: фронт (`loanProducts.ts`, `credit.ts`, `schema.ts`) и бэк (`loan.js`, `validate.js`). Сегодня их сверяют руками. Миграция на PHP — удобный момент, чтобы рассудить дублирование (например, PHP как единственный источник правды для расчёта и валидации, а фронт — только для UX-подсказок), но до этого момента правки ставок/лимитов/текста должны вноситься в обе стороны.
2. **Проверка «платёж ≤ 50 % дохода» есть только на фронтенде** (`MAX_PAYMENT_TO_INCOME_RATIO = 0.5` в `credit.ts`, ещё и вычисляется «рекомендуемый доход» `ceil(payment / 0,5 / 100) × 100`). **Сервер этот критерий не проверяет** — доход может быть сколь угодно мал относительно платежа, заявка всё равно принята и сохранена. Миграции нужно решить: переносить на сервер ради консистентности (с переводом текста Validation UI-ошибки на сервер) или оставить как есть, только задокументировать.
3. **Порядок округлений и типы `NUMERIC` в JSON-ответе** (строки с двумя знаками) — критичны для бит-в-бит совпадения (см. §6.2, §4.2).
4. **Расхождение в `POST /admin/:id/status`** (JSON-тело vs urlencoded-форма) — самое вероятное место, где текущее поведение и «задумка» расходятся (см. §4.4); при переписывании принять осознанное решение.
5. **Миграции БД** без версионирования; `ALTER`-ы не применяются к живым базам (см. §3).
6. **Все ошибки через 500 `internal_error`**, включая битое JSON-тело (там обычно ждут 400) — если сохранять «как есть», не удивляться внешним наблюдениям о статус-кодах; лучше при переписывании разделить 400/500.
7. **Basic-аутентификация админки** — сравнение пароля — с постоянным временем выполнения (защита от атак по таймингу); в PHP использовать аналогичное (`hash_equals`), реальном `realm="admin"`.
8. **Локализация**: все пользовательские строки (тексты ошибок, статусы, заголовки админки) — на русском; их нельзя менять/переводить, иначе рассыпется соответствие между фронт-валидацией и серверной `issues[0].message`.
9. **Семантика `fullName`**: допускает любые пробельные символы (в т.ч. переводы строк) внутри строки — тестовые кейсы для PHP-валидатора стоит взять отсюда.
10. **Сервер стартует с автоприменением схемы БД**; при недоступной БД процесс стартует, но падает сразу после — PHP-версия (обычно без «демон-процесса») должна решить эквивалентное поведение: например, проверять БД при старте либо при первом запросе.
